# ZHA to Z2M Migration Tool

A browser-based tool that migrates a Home Assistant **ZHA** Zigbee network to
**Zigbee2MQTT (Z2M)** - generating a matching `configuration.yaml` and the
device database entries Z2M needs, so your existing devices reconnect to the
same Zigbee network instead of having to be re-paired one by one.

Everything runs entirely client-side in your browser (a SQLite database is
read via [sql.js](https://github.com/sql-js/sql.js) compiled to WebAssembly).
None of your Home Assistant data is uploaded anywhere.

## Why this exists

Home Assistant's built-in ZHA integration and the Zigbee2MQTT add-on are two
different, mutually exclusive ways to talk to a Zigbee coordinator. Switching
from one to the other normally means re-pairing every single Zigbee device -
tedious at best, and painful if you have battery-powered devices mounted in
hard-to-reach places.

Because both ZHA and Zigbee2MQTT ultimately store the same kind of
information (the network's PAN ID, extended PAN ID, channel, and network
key, plus a per-device address book), it's possible to carry that information
over directly. This tool automates extracting it from ZHA's SQLite database
and Home Assistant's device/area registries, and turns it into the files
Zigbee2MQTT expects.

## Features

- **Generates `configuration.yaml`** with the `advanced` network settings
  (`pan_id`, `ext_pan_id`, `channel`, `network_key`) copied from your ZHA
  backup, plus a `devices` map of IEEE address for friendly names.
- **Merges into an existing `configuration.yaml`** (optional) instead of
  only producing a fragment, so you get one complete, ready-to-use file.
- **Room-aware friendly names**: Home Assistant only requires a device name
  to be unique within a room, but Zigbee2MQTT requires it to be unique
  network-wide. When you provide `core.area_registry`, any device assigned
  to a room gets that room appended to its name (e.g. `Lamp 2 (Kitchen)`),
  avoiding collisions.
- **Auto-detects ZHA's SQLite schema version** (`devices_v12`, `_v13`,
  `_v15`, ...) instead of hardcoding one, since Home Assistant has bumped
  this more than once.
- **Appends devices into Zigbee2MQTT's `database.db`**, so devices are
  recognized by their existing network address instead of needing to
  re-join the network.
- **Generates `coordinator_backup.json`** (optional, see caveat below) in
  the format zigbee-herdsman expects, as an alternative way to restore the
  exact original network onto the coordinator.

## Getting started

```bash
npm install
npm start   # starts the Vite dev server with hot reload
```

The project is built with [Vite](https://vite.dev/): `index.html` at the repo
root is the entry point, `src/*.ts` is the TypeScript source. `npm run build`
type-checks (`tsc --noEmit`) and produces a complete, self-contained `dist/`
folder — that's what's served in production and gitignored locally, since
it's fully regenerated by the build. Use `npm run preview` to serve that
production build locally instead of the dev server.

## Usage

The tool walks you through four steps; each is also explained in the app
itself.

### Locating the files

There are two ways to get at these files, depending on what you have access to:

**Option A — the File editor add-on.** Install the official
[File editor](https://github.com/home-assistant/addons/tree/master/configurator)
add-on from the Home Assistant add-on store, then browse directly to the
paths in the table below (no export/extract step needed). This is also the
easiest way to handle Steps 2-4 below: uploading the generated
`configuration.yaml`, deleting the stale `database.db`/`state.json`, and
downloading the fresh `database.db` that Zigbee2MQTT creates.

**Option B — a full Home Assistant backup.** Export a backup (a single
`.tar` file), extract it, then extract the `homeassistant.tar.gz` inside it
(gunzip, then untar). That produces a `homeassistant/` folder — the files
below all live under `homeassistant/data/`.

| File | Path via File editor / in the backup | Used in |
|---|---|---|
| ZHA's database | `data/zigbee.db` | Step 1 (required) |
| Device registry | `data/.storage/core.device_registry` | Step 1 (required) |
| Area registry | `data/.storage/core.area_registry` | Step 1 (optional) |
| Zigbee2MQTT's existing config | `data/zigbee2mqtt/configuration.yaml` | Step 1 (optional) |
| Zigbee2MQTT's device database | `data/zigbee2mqtt/database.db` | Step 3 (required) — only exists *after* Z2M's first successful start |

### Step 1 — Generate `configuration.yaml`

Upload `zigbee.db` and `core.device_registry` (required), plus
`core.area_registry` and an existing `configuration.yaml` (both optional, see
above). Click **Generate configuration.yaml**.

### Step 2 — Start Zigbee2MQTT once to form the network

This happens outside the tool, directly in the Zigbee2MQTT add-on. The File
editor add-on (see above) is the easiest way to do the delete/upload/download
steps below without needing a full backup export:

1. Stop the add-on if it's running.
2. In its data folder, delete any existing `database.db` and `state.json`
   (and `coordinator_backup.json`, unless you're deliberately testing that
   optional file from Step 1).
3. Upload the `configuration.yaml` generated in Step 1, replacing the
   existing one.
4. Start the add-on and confirm a clean startup in its log - it will form a
   network identical to your original ZHA one, using the network settings in
   `configuration.yaml`.
5. Stop the add-on again. It will have created a fresh `database.db`
   containing just the coordinator entry - download it via File editor.

### Step 3 — Add your devices to `database.db`

Upload the fresh `database.db` from Step 2 into the tool and click
**Add devices to database.db** to append every device from your ZHA backup
into it.

### Step 4 — Finish the migration

Upload the updated `database.db` back into the add-on's data folder (e.g. via
File editor), overwriting the one from Step 2, and start Zigbee2MQTT again. Devices will
appear as "unsupported" - interview each one from the Zigbee2MQTT frontend
to complete the migration. Interview mains-powered routers first, then other
mains-powered devices, then battery-powered devices last (you'll need to
wake each battery-powered device manually).

## Caveats

- **`coordinator_backup.json` is optional and untested against a real
  add-on start.** It has been validated against zigbee-herdsman's own source
  code (the exact field layout and byte encoding it expects), but Zigbee2MQTT
  forms an identical network from `configuration.yaml` alone on its first
  start - which is the standard way this migration is done and doesn't rely
  on this file at all. Treat it as an experimental alternative, not a
  required step.
- The `coordinator_backup.json` generator currently only supports
  **EZSP-based coordinators** (e.g. Sonoff/SLZB dongles) - it reads
  EZSP-specific fields from the ZHA backup and will throw a clear error if
  they're missing.
- This tool only carries over network settings and device identities. It
  does **not** migrate automations, dashboards, or per-device configuration
  (e.g. exposed entities) - those live in Home Assistant itself and are
  unaffected by the ZHA -> Z2M switch.
